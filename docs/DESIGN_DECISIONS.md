## 一、这份文档的用途

下次你要设计一个"多角色协作 + 人类决策"的工具类产品时，把这份文档丢给 AI 或设计师，作为起点而不是从零开始。

它回答两个问题：
- **页面应该长什么样**（交互设计逻辑）
- **业务应该怎么建模**（Multi-Agent 逻辑）

## 二、交互设计逻辑

### 2.1 三栏布局的颜色语义

```
左栏 #f1f5f9（冷灰）  中栏 #ffffff（纯白）   右栏 #fffbeb（暖黄）
────────────────────  ────────────────────  ────────────────────
背景 / 索引            主内容                需要你行动
退到视觉背景           最亮最干净             天然成为焦点

议题列表               研判对话线程           当前决策对象
生命周期状态标签        Agent 发言气泡         证据账本摘要
责任方标注             状态流转卡             执行验证闭环
```

**核心原则：冷色 = 信息背景，暖色 = 需要行动。**

这个颜色逻辑不依赖具体业务，可以直接迁移到任何三栏工具类产品。

### 2.2 状态驱动 UI

卡片的视觉样式由状态决定，不是手动控制颜色。

```
P0 风险议题  → 红色左边框 + 红色 badge
P1 风险议题  → 橙色左边框 + 橙色 badge
联合研判中   → 蓝色脉冲动画
等待拍板     → 琥珀色高亮 + 右栏聚焦
已沉淀       → 灰色降调
```

**好处**：设计师只需要定义状态→样式的映射表，不需要为每个场景单独设计。新增状态只改映射表，不改组件。

### 2.3 信息分层：发言和证据分离

对话气泡只显示结论和判断，证据单独在右栏展示。

```
中栏气泡（结论层）          右栏证据账本（依据层）
─────────────────          ─────────────────────
"建议续约，但需降租"  ←──→  经营数据：近3月销售-34%
                            历史案例：同类商户降租后恢复率72%
                            现场证据：装修老化，客流动线差
```

**为什么这样设计**：AI 的结论如果没有可追溯的依据，用户不会信任。把证据单独结构化存储，让"可解释性"变成产品功能而不是聊天记录。

### 2.4 状态流转卡：让工作流进展可见

每次议题状态变化，在对话线程里插入一张状态流转卡，而不是只改左栏的标签。

```
┌─────────────────────────────────┐
│  🔄 状态流转                     │
│  联合研判中  →  等待拍板          │
│  触发：任务调度官收敛3个方案       │
│  下一步：总经理拍板               │
└─────────────────────────────────┘
```

**为什么这样设计**：工作流的进展不应该只反映在状态标签上，用户需要在主内容区感知到"发生了什么"。状态流转卡让时间线完整，也让演示更有节奏感。

### 2.5 AutoPlay 演示引擎

产品演示不依赖真实 AI 调用，用脚本驱动。

```typescript
// 每条消息是一个脚本节点
{ agentId, content, delay, lifecycle?, evidence?, decision? }
```

**为什么这样设计**：
- 演示完全可控，不依赖网络和 AI 服务
- 每次演示路径一致，适合面试和汇报
- delay 模拟思考时间，让演示有真实感
- 脚本即文档，产品逻辑一目了然

**迁移建议**：任何需要"可控演示"的 portfolio 项目都可以用这个模式，把真实的 AI 调用替换成脚本驱动。

## 三、Multi-Agent 业务逻辑

### 3.1 角色设计原则：权限边界比人格更重要

每个 Agent 最重要的不是说话风格，而是：

```
能看什么信息
能输出什么判断
不能拍什么板
什么时候必须停下来等人类
```

**反例**：给 Agent 写"你是一个严谨的财务分析师，说话简洁专业"——这是人格描述，不是权限边界，对系统可信度没有帮助。

**正例**：财务分析师只能输出数据解读，不能输出续约建议，遇到数据造假迹象必须升级给人类。

### 3.2 议题生命周期状态机

议题是有状态的业务对象，不是一条消息。

```
自动识别 → 建议升级 → 联合研判中 → 等待请示 → 等待拍板
                                                  ↓
已沉淀 ← 待复盘 ← 执行中 ← 已拍板 ←─────────────┘
```

每个状态必须定义：
- 当前责任方（Agent 还是人类）
- 进入条件
- 下一步动作
- 是否需要人类介入

**关键设计决策**：状态机的转移规则必须在配置里，不能硬编码在组件里。否则换一个场景就要重写逻辑。

### 3.3 决策对象：拍板是业务对象不是按钮

```typescript
interface DecisionObject {
  question: string           // 决策问题（具体，不模糊）
  options: Option[]          // 可选方案（可比较，不是建议）
  recommendedOption: string  // 推荐方案
  recommendReason: string    // 推荐理由
  keyEvidence: string[]      // 关键依据（来自证据账本）
  risks: string              // 风险与代价
  deadline: string           // 截止时间
  verificationMetrics: string[] // 验证指标（领先指标）
  result?: string            // 实际决策结果
}
```

**为什么这样设计**：如果"拍板"只是一个按钮，人类不知道自己在决定什么。把决策结构化，强迫系统在请求人类决策之前把问题、选项、依据都准备好。

### 3.4 证据账本：让 AI 发言可追溯

```typescript
interface EvidenceItem {
  type: '经营数据' | '现场证据' | '历史案例' | '招商判断' | '活动数据' | '客诉反馈'
  summary: string
  provider: string        // 哪个 Agent 或人类提供
  credibility: 'high' | 'medium' | 'low'
  supportsJudgment: string // 支撑哪个判断
}
```

**为什么这样设计**：AI 的可信度来自可追溯性。证据账本让每一个判断都有来源，让人类在拍板前能审查依据质量。

### 3.5 执行验证闭环

拍板后不只生成任务，还追踪结果。

```
执行任务 → 预期领先指标 → 实际结果 → 是否达标 → 复盘结论 → 沉淀为组织记忆
```

**关键设计决策**：验证指标必须是领先指标（2周内能看到变化），不能是滞后结果（季度营收）。否则等到能验证的时候，已经来不及纠偏。

## 四、两层设计的关系

```
交互设计层                    业务逻辑层
──────────────────────────────────────────────────
三栏布局          ←映射→     议题列表 / 研判线程 / 决策面板
状态驱动 UI       ←映射→     生命周期状态机
信息分层          ←映射→     发言 vs 证据账本
状态流转卡        ←映射→     状态机转移事件
AutoPlay 引擎     ←映射→     脚本化的 Agent 发言序列
右栏暖黄聚焦      ←映射→     当前需要人类行动的决策对象
```

**核心洞察**：交互设计的每一个决策都有对应的业务逻辑支撑。颜色不是装饰，布局不是习惯，它们是业务语义的视觉表达。

## 五、下次复用时的最小起点

如果你要用这套模式做一个新场景，最小需要定义：

```
1. 触发事件是什么
2. 需要哪些角色（每个角色一句话说清楚能做什么、不能做什么）
3. 生命周期有哪些状态（建议不超过 8 个）
4. 人类在哪个节点拍板、拍什么
5. 拍板后用什么指标验证（必须是领先指标）
```

定义完这 5 件事，三栏布局、状态卡片、证据账本、AutoPlay 引擎都可以直接套。

场景设计 prompt 见：`docs/SCENARIO_DESIGN_PROMPT.md`

## 六、已知局限

这套设计目前不适合以下情况：

- 多议题并行且需要合并判断
- 多层级审批链（A 批完 B 再批）
- 角色动态加入和退出
- 接入真实 LLM 后的消息一致性
- 需要实时数据刷新后重新判断

这些是 v2 的问题，不是现在要解决的。
